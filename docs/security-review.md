# Security review

Reviewed: 2026-11-04, updated 2026-11-06 · Scope: v2 (branch `v2-saas`): application code, API routes, the AI runtime, deployment configuration, dependencies.

## Summary

The app has no real accounts and moves no real money. Visitors pick a demo persona from a list. The sample portfolio is shared and read-only; each visitor's changes sit in a private overlay (Cloudflare D1, or SQLite in Docker) that is wiped at midnight Pacific time.

The main risks in v2 are:

- reads and writes outside a persona's scope;
- workflow and money rules skipped through generic edits;
- AI agents or model output acting on data;
- abuse of the public AI routes;
- leaked secrets.

Each has a control below. Issues found and fixed during the v2 build, and the remaining gaps, follow.

## Controls in place

| Area | Risk | Control | Where |
| --- | --- | --- | --- |
| Scope | Reading another region's or person's records | Every list, facet, metric and download (CSV, Excel, PDF) filters to the persona's properties in SQL (`scopeWhere`); report and owner-statement downloads re-run the report under the same role and scope checks as the page. Portal users (owner, resident, vendor, applicant) get only rows tied to their own record (`selfClause`); any other entity returns no rows | `src/server/query.ts`, `src/server/permissions.ts` |
| Permissions | Acting outside a role | A role × module matrix (none, read, write, approve) plus per-definition role lists; named actions list their roles; staff pages redirect portal personas to their portal | `src/auth/personas.ts`, `src/entities/registry.ts`, `src/auth/session.ts` |
| Generic writes | Writing outside scope | The scope check runs inside the write batch, so a refused create or edit writes nothing. Every reference must point at a record in scope. New ids never reuse a base or workspace id | `src/server/query.ts` (`scopeGuard`, `assertRefs`, `newId`) |
| Generic writes | Skipping a workflow step | Ledger tables (charges, payments, credits, deposits, bank accounts, bank transactions, reconciliations, journal entries, owner distributions) are actions-only (405). Fields marked `system` change only through named actions; create accepts only their initial value. `lockedWhen` refuses edits and deletes of locked records (409) | `src/entities/types.ts`, `src/server/query.ts`, `src/entities/defs/*` |
| Money | Overdraw, double payment | Each money action is one D1 batch whose first statement inserts the transfer only if the SQL guards hold; later statements run only if it exists. A unique index allows one live transfer per key, and guards also check base transfers for the key. Available trust is recomputed in SQL | `src/server/money.ts`, `src/server/data.ts` |
| Money | Approving outside one's authority | Each money action checks the role's approve right and the property scope again. Maintenance spend above the owner threshold needs the owner's recorded approval, checked in JavaScript and SQL. Work orders pay only an invoiced amount, never the editable estimate | `src/server/money.ts` |
| Money | Paying a changed bank account | No bill or work-order payout while an unverified vendor bank change is open (`NO_FRAUD_HOLD`). A bank change must be verified by someone other than the person who entered it, read from the audit log. Only that callback (`vendors.confirm_bank_change`) closes the issue: approving the hold proposal (Data Health fix or Payables Agent) takes the vendor off work and assigns the call, and payments stay held. Only the principal or a payables approver can dismiss the flag. Vendor bank details change only through the bank-change action | `src/server/money.ts`, `src/extensions/payables/actions.ts` |
| Money | Wrong deposit deductions | A disposition refuses charges that are unknown, on another lease or repeated, in JavaScript and in the guarded insert; each deduction must fit the charge's open balance | `src/server/money.ts` (`disposeDeposit`) |
| AI proposals | A stale or out-of-scope proposal running | Agents may propose only registered actions. Before an approved proposal runs, the server re-checks that the record is in the approver's scope, that its key fields match the agent's snapshot, that the action's precondition holds and that the role may run it. A guarded `ai_decisions` insert runs it once. Only staff decide proposals; an owner decides only spend waiting on them for a property they own. The generic action route (`/api/e/<entity>/<id>/actions/<ai action>`) applies the same `canDecide` check: a money, legal or safety proposal the caller can't approve stays in the inbox (202 with the proposal id); a low-risk one is refused (403) | `src/ai/effects.ts`, `src/ai/http.ts`, `src/ai/actions.ts` |
| AI proposals | Applying a money, fraud or legal fix from Data Health | Fixes are always-human when they touch money, fraud or legal status, a bill or bill line, a GL account or any amount, or name an action with no field changes (those become a task); the agent never auto-applies them. Applying a fix from the Data Health page creates a proposal and never runs one that is always-human or not low risk: it waits in the approvals inbox (202 with the proposal id), whatever the clicker's role. A low-risk fix runs only if `canDecide` allows the clicker, in the single and bulk paths; otherwise it is queued too. The page labels such fixes "Send for approval" using the same rule (`queueReason`) | `src/ai/datafix.ts`, `src/ai/tools/write.ts`, `src/app/api/ai/data-health/*` |
| AI proposals | Pulling a vendor off emergency work | Taking a vendor with open emergency or life-safety work orders off work (stop assigning, a data fix, or a status edit to Inactive, Do not use or delete) follows the life-safety rule: only the principal or a regional manager decides. The proposal is flagged when written and the count is checked again at decision time; the generic record API refuses the status edit and the delete for other roles. A bank-change payment hold stays the accountant's call: when the vendor has such jobs (when the hold is proposed or when it is approved), the hold keeps the vendor on work and taking it off work becomes a separate proposal for the principal or a regional manager | `src/ai/life-safety.ts`, `src/ai/runtime.ts`, `src/ai/effects.ts`, `src/ai/decide.ts`, `src/ai/http.ts` (`canDecide`), `src/server/query.ts` (`updateRecord`, `deleteRecord`) |
| AI proposals | Property-scoped staff seeing org-level proposals | Data Health issues and agent proposals with no property show to property-scoped roles when the role can read that record type (vendors, owner entities): for example, a property manager sees vendor bank-change holds and owner-reporting messages on an owner entity. They can't decide what the decide rule gives to others, and can't dismiss critical, money or fraud issues | `src/ai/data.ts` (`scopeClause`, `orgIssueTypes`), `src/ai/tools/write.ts` (`canDismiss`) |
| AI settings | A scoped role changing org-wide agent behaviour | One rule (`canEditPolicies`: principal, regional manager, admin) gates agent on/off, autonomy and schedule (`PATCH /api/ai/agents/[key]`) and approval policies (`PATCH /api/ai/policies/[id]`, their only write path; generic writes return 405). Platform admins and property-scoped roles read only. Legal and safety policies can't be set to act alone | `src/ai/policy-editors.ts`, `src/app/api/ai/agents/[key]/route.ts`, `src/app/api/ai/policies/[id]/route.ts` |
| AI tools | The model reaching data or money directly | Tool inputs are zod-checked and each tool checks the caller's role. Read tools use the scoped query layer. Write tools only create proposals or drafts, and never touch ledger tables. Drafts with amounts not in the facts are rejected | `src/ai/runtime.ts`, `src/ai/tools/*` |
| AI output | Prompt injection, invented figures | Untrusted text (documents, messages, questions, record fields) is framed as data in every prompt. Model output is schema-validated. Agent proposals must match a rules candidate, and figures come from the rules. Assistant answers with a dollar figure no tool returned fall back to rules | `src/ai/agents/framework.ts`, `src/ai/assistant.ts`, `src/lib/llm.ts` |
| AI cost | Denial of wallet | 20 AI calls a minute per IP (the `AI_RATE_LIMITER` binding, keyed on `cf-connecting-ip`), including named actions that call a model. Each agent run has a step limit, a deadline and a 50-cent budget. A sweep covers at most 10 active workspaces | `src/lib/guard.ts`, `src/app/api/e/_lib/actions.ts`, `src/ai/orchestrator.ts` |
| Cron route | Anyone starting sweeps | `/api/ai/sweep` accepts a per-isolate token set by `scheduled()`, compared in constant time, or an admin session with approve rights | `src/worker-entry.ts`, `src/ai/sweep.ts` |
| Shared data | Visitors changing the shared base | Base rows are read-only at runtime; the cookie id pattern can never equal `base`. Scheduled agents run only in visitor workspaces, and nothing auto-applies in base | `src/server/workspace.ts`, `src/ai/runtime.ts` |
| Transport | Traffic read or changed on the network | On `propniti.ai` and `www.propniti.ai` the Worker answers plain HTTP with a 301 to the same URL on https before the app runs (it checks the request URL, `cf-visitor` and `X-Forwarded-Proto`), and refuses writes whose `Origin` is an `http:` page (403). Localhost, dev servers and other hosts are left alone. Production also sends HSTS (`max-age` two years, `includeSubDomains`, `preload`) | `src/worker-entry.ts`, `src/lib/https.ts`, `next.config.ts` |
| Writes | Cross-site requests | Writes need an `Origin` matching the host (403 otherwise); in production the origin must also be https (loopback hosts excepted, for local production builds). The workspace cookie `pn_ws` is HttpOnly, SameSite=Lax, and Secure in production | `src/app/api/e/_lib/http.ts` (`sameOrigin`), `src/ai/session.ts`, `src/server/workspace.ts` |
| Cookies | Cookies sent over plain HTTP | Every cookie the app sets is Secure on HTTPS: `pn_as` and `pn_ws` from the server in production; the browser-set preference cookies (`pn_theme`, `pn_density`, `sidebar_state`, `pn_layout`) and `pn_as` from the role switcher when the page is https. A malformed `pn_as` (bad percent-encoding) falls back to the default persona instead of a 500 | `src/lib/cookie.ts`, `src/auth/personas.ts`, `src/components/app/shell/`, `src/components/app/collapsible/prefs.ts` |
| Sign-out | The next person on a shared browser seeing the last visitor's changes | Sign-out (`DELETE /api/session`, called by "Sign out of demo" and "Exit") clears both `pn_as` and `pn_ws` (`Max-Age=0`, same flags as when set); `pn_ws` is HttpOnly, so only the server can clear it | `src/app/api/session/route.ts`, `src/components/app/shell/persona.ts` |
| Writes | Request and storage abuse | 60 writes a minute per IP; bodies read as a stream and abandoned past the cap (64 KB records, 16 KB AI, 4 MB uploads); zod schemas on every body; at most 30 new workspaces per IP an hour; pages capped at 100 rows and CSV, Excel and PDF downloads at 10,000 (downloads share the write limit); spreadsheet formula injection is neutralised in CSV (leading `'`) and Excel (text cells only, never formulas, `quotePrefix` style) | `src/lib/guard.ts`, `src/server/workspace.ts`, `src/server/query.ts`, `src/lib/export/` |
| Imports | Bulk writes past role, scope or limits | Files are parsed in the browser; the server takes only cleaned records (4 MB body; zod caps, enums for unit status and property type, end dates not before start dates), re-matches them to existing records, and creates only what the role may create (entity create rights; ledger records for staff who can record payments) at in-scope properties. Opening balances go only on leases the same import creates, never on a ledger already on file. One batch behind a unique audit lock row, so a repeat writes nothing. Undo deletes only that batch's overlay rows; it is refused when any batch row is at a property outside the actor's scope, or when any live row outside the batch points at a batch row through any id column (map derived from the migrations and checked by a test; logs and agent output excepted). The AI pass receives only headers, 5 sample rows and 30 flagged cells (60 characters each), trimmed whole to a 20,000-character budget, under the AI rate limit. XLSX unpacking counts real inflated bytes and stops at 30 MB | `src/extensions/import/server.ts`, `src/extensions/import/refs.ts`, `src/extensions/import/ai.ts`, `src/extensions/import/parse.ts`, `src/app/api/import/*` |
| Uploads | Malicious or wrong files | 4 MB cap; type decided by file signature (JPEG, PNG, WebP, PDF); anything else returns 415. Files are read in memory and discarded | `src/app/api/ai/extract/route.ts` |
| Documents | Unsafe links | One rule (`SAFE_LINK`) on write and on render: a same-site path or an `https://` link. Paths starting `//` or `/\` are refused (browsers read both as another host), as are control characters (browsers drop tabs and newlines, so `/<tab>/x` would become `//x`), `http:`, `javascript:` and `data:` | `src/lib/links.ts`, `src/entities/defs/communications.ts`, `src/components/entity/pages.tsx`, `src/components/app/record/DocumentsPanel.tsx`, the owner and resident portal document pages |
| Output | XSS | Model and user text render as React text. There are three `dangerouslySetInnerHTML` uses, none with user or model text as HTML: the docs page renders the repo's own markdown (`content/docs/`, bundled at build time); `ThemePreload` writes an inline script whose only input is the theme mode, narrowed to `light`, `dark` or `system` by `themeMode()` and written with `JSON.stringify`; the chart `<style>` (`ChartStyle`) writes CSS variables from the chart config. Its keys and colors come from code (entity definitions, the palette), except donut charts, whose keys are the category values. Those charts render only in the browser (`ssr: false`), where `<style>` content is set as raw text, so a value can't open a tag or run script; at worst it adds CSS rules, and the CSP blocks loads from other hosts | `src/app/docs/[slug]/page.tsx`, `src/components/app/ThemePreload.tsx`, `src/components/ui/chart.tsx`, `src/components/app/dashboard/Charts.tsx` |
| Browser | Clickjacking, sniffing | In production: CSP (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`), HSTS, `nosniff`, `X-Frame-Options: DENY`, Referrer-Policy, Permissions-Policy; `X-Powered-By` removed | `next.config.ts` |
| Errors | Leaking database internals | AI routes (`guarded`), Data Health results and run steps show "The database is busy; try again in a moment" (503 from routes) for D1 and SQLite errors; the detail goes to the server log only | `src/ai/http.ts` |
| Errors | Leaking model-provider errors (request ids, key fragments, raw replies) | Model calls in the AI runtime go through `currentModel()`, which logs the provider's error in full with the `[ai]` prefix and throws a short reason ("model unavailable", "model timed out"). Run traces keep only that reason; features with a fallback say "The AI service didn't respond, so this uses the rule-based answer."; routes without one answer 503 "The AI service didn't respond. Try again in a minute." The older calls in `src/lib/llm.ts` (invoice and certificate reading, work-order checks) log the error the same way and show a fixed note, with the rule-based or mock result | `src/ai/providers/index.ts`, `src/ai/http.ts`, `src/lib/llm.ts` |
| Precompute | Writing base data from outside | `/api/ai/precompute` answers only on localhost with a token, or in dev; 404 otherwise | `src/app/api/ai/precompute/route.ts` |
| Secrets | Keys in the repo | No secrets committed; Worker secrets set with `wrangler secret put`; the placeholder `unset` counts as no key | `cloudflare.config.ts`, `src/lib/llm.ts` |
| CI | Supply chain | `npm ci`; lint, type check, tests and both builds on every push to main and every pull request. Third-party actions are pinned to full commit SHAs (tag in a comment); workflows get a read-only token (`permissions: contents: read`) | `.github/workflows/ci.yml`, `.github/workflows/eval.yml` |

## Dependencies

`npm audit --omit=dev` (2026-11-04): 11 findings, 9 moderate and 2 low, none high.

- **`fflate`** (through `satori` → `@vercel/og` → `vinext`): ZIP64 parsing in `unzipSync`, used by Open Graph image generation, which this app does not use.

## Known gaps

From the code and from the post-demo backlog in `research/gate-checklist.md`.

- **No authentication.** Anyone can pick any persona. The sign-in form's demo password is published on the page; `/api/session` checks it server-side in constant time (same-origin, write rate limit, `next` limited to `/app` and `/portal` paths), but it is a demo convenience, not an account system. The persona cookie `pn_as` is not HttpOnly (the role switcher sets it in the browser) and is not a security boundary. Before real data: an identity provider, server-side sessions and role checks bound to the signed-in user.
- **The workspace cookie is the only key** to a visitor's changes.
- **No per-org AI quota.** Limits are per IP and per run. `org_usage_monthly` holds seeded display data only.
- **Approval policies are partly enforced.** On money actions only the owner threshold for maintenance spend is enforced. Other limits, `approver_role` and `always_human` route AI proposals only. The fraud check on bill approval (not payment) runs in JavaScript, not SQL.
- **Owner policy overrides don't apply to agents.** Agents read only the org-default approval policies; owner-entity overrides are stored and shown but not used when an agent decides what may run on its own.
- **Fields still editable through generic writes** until their modules add named actions: lease status, budget status and approval, capex, 1099s, legal cases, service requests and message threads.
- **Shared rate-limit namespaces.** The preview and production Workers use the same limiter namespaces (1001, 1002).
- **AI runtime writes to base.** Cleanup of stuck runs (`reapStaleRuns`) updates and deletes some AI run rows without a workspace filter, and the sweep slot is one global `meta` row.
- **Banking scope** uses the owner entity's lowest property id. That matches "any of its properties" today only because every owner entity sits in one region.
- **`'unsafe-inline'` in the CSP**, required by hydration. Move to nonces when the runtime supports them.
- **Approximate rate limits.** Cloudflare's limiter counts per location and is eventually consistent; off Cloudflare the fallback is in memory per instance. Add a WAF rule for a hard cap.

## Open infrastructure items (need the owner's decision)

These are Cloudflare settings, not code; nothing here has been changed.

- **The preview Worker shares the production database.** `propniti-v2-preview.dnyana.workers.dev` uses the same D1 database (`propniti-v2`) as production, so preview builds read and write production's visitor workspaces. Give the preview its own D1 database.
- **Production is also reachable on workers.dev.** `cloudflare.config.ts` sets `workersDev: true`, so the production Worker answers at `property-mgmt-ai-prototype.dnyana.workers.dev` as well as `propniti.ai`. That host isn't in the HTTPS redirect list and has no zone settings (WAF rules, analytics). Set `workersDev: false` if nothing depends on it.
- **"Always Use HTTPS" zone setting.** The Worker now redirects plain HTTP on `propniti.ai` and `www`; turning on the zone's "Always Use HTTPS" would do it at the edge as well, including for paths that never reach the Worker.
- **HSTS preload.** `next.config.ts` sets `Strict-Transport-Security` with `preload`, which only takes effect once the domain is submitted to the browser preload list (hstspreload.org). Preloading makes browsers use https on the first visit too; it is slow to undo, and every subdomain must serve https first.
